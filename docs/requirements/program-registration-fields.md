# Program-Specific Registration Requirements

## Purpose

Define the shared and program-specific registration requirements for the
Archdiocese of Nyeri Youth Registration & Management System.

The system must support different registration fields and validation rules
for each program while maintaining a shared member identity.

---

## 1. Shared Member Information

These fields are shared across applicable programs.

| Field | Required | Notes |
|---|---|---|
| full_name | Yes | Member's full name |
| username | Yes | Unique login identifier |
| password | Yes for account creation | Must be securely hashed |
| phone | No | May be shared by multiple members |
| email | No | May be shared by multiple members |
| gender | No | Confirm allowed values |
| dob | No | Used for age and eligibility checks |
| local_church_id | Yes where applicable | Must belong to the selected parish and deanery |
| program_id | Yes | Identifies the selected program |

The official membership number and technical UUID are generated by the system.

## 8. Bulk Registration Requirements

Each program must have a program-specific import template.

The bulk import process must support:

- CSV and Excel input
- Program-specific column definitions
- Required and optional fields
- Server-side validation
- Hierarchy validation
- Duplicate detection
- Shared email and phone numbers
- Row-level error reporting
- Preview before import
- Idempotent processing
- Import summaries
- Audit logging
- Membership number generation
- Safe account creation or linking

Email and phone numbers must not be treated as unique identifiers.

The username, membership number, and technical UUID have different identity
and uniqueness responsibilities.

---

## 9. Implementation Policy

Do not finalize program-specific fields that have not been approved by the
responsible program administrators.

Use configurable program definitions where practical. Store additional
enrollment information in `extra_data` initially, and normalize fields
when reporting, searching, constraints, or operational requirements justify
doing so.

All authoritative validation must occur on the backend.
